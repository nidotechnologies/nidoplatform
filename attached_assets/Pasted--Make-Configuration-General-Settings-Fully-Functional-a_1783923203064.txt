# Make Configuration → General Settings Fully Functional and Drive the Entire Platform

## Objective

Convert all pages under **Configuration → General Settings** from static UI pages into fully functional system configuration modules.

The settings configured here must become the single source of truth for the entire NIDO Procurement Platform.

Every change made in these configuration pages must automatically reflect throughout the application in real time without requiring manual code changes.

There must never be duplicate configuration values stored in multiple places.

---

# General Principle

Treat the Configuration module as the platform's **Global Configuration Engine**.

Whenever a setting is updated, every page, component, layout, API, dialog, report, and workflow that depends on that setting should automatically use the updated value.

Do not hardcode configuration values anywhere in the application.

Always read them from the configuration service or database.

---

# Configuration Sections

## 1. Organization

This section should control the organization's information across the entire application.

Fields may include:

* Organization Name
* Display Name
* Logo
* Favicon
* Website
* Email
* Phone
* GST Number
* PAN
* CIN
* Address
* Registered Address
* Billing Address
* Support Email
* Support Phone
* Social Links

Whenever any of these values are updated:

Automatically update throughout the application, including but not limited to:

* Header
* Sidebar
* Login Page
* Footer
* Dashboard
* Reports
* Invoices
* Purchase Orders
* Quotations
* Contracts
* Email Templates
* PDF Documents
* Printable Documents
* Notifications
* Support Pages
* Company Information Cards
* Profile Pages

No page should require manual updates.

---

---

# Live Configuration Engine

Create a centralized Configuration Service.

Every module must obtain its configuration values from this service.

Do not allow modules to maintain their own copies of configuration values.

There must be only one source of truth.

Whenever configuration changes:

* Refresh application state automatically.
* Update all dependent components.
* Apply changes immediately.
* Avoid requiring users to refresh the browser whenever possible.
* Ensure all future pages automatically consume configuration from this service.

---

# Owner Platform

Only the NIDO Owner (Super Admin) can access and modify these General Settings.

These settings are global and affect the entire platform.

No Client Portal user should be able to access or modify them.

---

# Future Scalability

Design the configuration system so additional configuration sections can be added without changing the overall architecture.

Every new configuration module should automatically integrate with the centralized Configuration Service.

---

# Expected Result

The Configuration → General Settings module should become the platform-wide configuration engine.

Every setting changed by the NIDO Owner should immediately and consistently affect the relevant parts of the application in real time.

The application should no longer rely on hardcoded values for organization details, branding, localization, procurement defaults, notifications, or security. Instead, all modules should dynamically read from the centralized configuration system, ensuring a single source of truth, real-time updates, and a scalable architecture.
