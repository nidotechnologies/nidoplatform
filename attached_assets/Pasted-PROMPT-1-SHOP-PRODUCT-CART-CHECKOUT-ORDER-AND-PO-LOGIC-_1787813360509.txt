# NIDO — Add Physical and Digital Shop Support

## IMPORTANT

Do not rebuild, redesign, or replace existing NIDO modules.

The current NIDO procurement flow is already working. Make only the smallest required changes.

Before coding:

1. Inspect the existing codebase.
2. Identify the current Product, Vendor, Client Catalogue, Shop, Product Details, Cart, Checkout, Order, Order Item, Inventory, and PO logic.
3. Reuse existing models, APIs, components, services, authentication, and UI.
4. Do not create duplicate modules, pages, APIs, database tables, or frameworks.
5. Do not change the existing Physical Product workflow except where required to support Digital Products.
6. Do not build the detailed Digital Order Details page yet.
7. Do not add mock data unless required for testing.
8. Do not refactor unrelated code.
9. Keep the implementation small and incremental to reduce Replit usage.

---

The existing Physical Product flow must continue working exactly as it does:

→ Publish Product

* Digital Product: NIDO internally uses the configured default/preferred supplier.

The customer must never be required to select the Digital supplier.

Do not create duplicate supplier structures.

PROMPT 2 — DIGITAL FULFILLMENT BACKEND FOUNDATION

# NIDO — Digital Fulfillment Backend Foundation

## IMPORTANT

Do not rebuild, redesign, or replace existing NIDO modules.

This prompt is only for creating the minimum backend/data foundation for Digital Fulfillment.

The Shop, Product, Cart, Checkout, Order, and PO changes are handled separately.

Before coding:

1. Inspect the existing codebase.
2. Identify the existing Order, Order Item, Product Type, Vendor/Product relationship, file storage, authentication, authorization, RBAC, and audit systems.
3. Reuse existing models, APIs, services, storage, authentication, and authorization.
4. Do not create duplicate Order, Product, Vendor, or file systems.
5. Do not build the detailed Digital Order Details page yet.
6. Do not redesign the existing Order page.
7. Do not add unnecessary dependencies.
8. Do not create mock data unless required for testing.
9. Make the smallest possible implementation to reduce Replit usage.

---

# 1. DIGITAL FULFILLMENT CREATION

When a Digital Order Item is created, create one Digital Fulfillment record.

Initial status:

```text
PENDING
```

The Digital Fulfillment record must be linked to:

* Client Order
* Digital Order Item
* Digital Product
* Client
* Internal supplier/vendor if available

Do not create a separate customer order for Digital Products.

---

# 2. DIGITAL FULFILLMENT STATUSES

Use the minimum status structure required for the future workflow.

Suggested statuses:

* PENDING
* LICENSE_UPLOADED
* PENDING_RELEASE
* RELEASED
* DOWNLOADED
* COMPLETED
* CANCELLED

If the existing system already has an equivalent status structure, reuse it.

Do not create duplicate status systems.

The Client Order status and Digital Fulfillment status must remain separate.

Example:

```text
Client Order: PROCESSING
Digital Fulfillment: PENDING
```

---

# 3. DIGITAL FULFILLMENT DATA MODEL

Inspect the existing schema first.

Only add fields or a table if an equivalent structure does not already exist.

A minimum Digital Fulfillment record should support:

* id
* order_item_id
* order_id if required by existing relationships
* product_id if required by existing relationships
* client_id if required by existing relationships
* supplier/vendor reference if needed
* status
* license file reference or secure storage path
* license file name
* encrypted password
* uploaded_by
* uploaded_at
* released_by
* released_at
* downloaded_at
* completed_at if needed
* cancelled_at if needed
* created_at
* updated_at

Do not add duplicate fields if the existing Order Item already provides the relationship.

Use existing naming conventions.

Use existing migration and schema tools.

---

# 4. LICENSE FILE SUPPORT

Prepare the backend to support one password-protected license/digital asset file per Digital Fulfillment record.

Reuse the existing NIDO file/storage system if available.

The system should support:

* Secure file storage reference
* Original file name
* Stored file name or storage key
* File metadata if already supported
* Upload timestamp
* Uploading user
* Release timestamp
* Releasing user
* Download timestamp

Do not build a complicated file management system.

Do not expose the file before it is released.

---

# 5. PASSWORD SECURITY

The license file password must be securely stored.

Requirements:

1. Never store the password as plain text.
2. Encrypt the password using the existing encryption/security utility if available.
3. If no encryption utility exists, use the project’s existing secure secret/encryption approach.
4. Do not return the password through client-facing APIs.
5. Do not include the password in normal order responses.
6. Only authorized internal users may create or update the password.
7. Do not log the password.
8. Do not expose the password in error messages.

The client will receive the password separately through an approved communication method.

---

# 6. FUTURE DIGITAL LICENSE WORKFLOW

Prepare the backend for this workflow:

Order Created
→ Digital Fulfillment = PENDING
→ Authorized NIDO employee uploads password-protected license file
→ Authorized NIDO employee manually enters the file password
→ File is stored securely
→ Password is encrypted and stored
→ Fulfillment becomes LICENSE_UPLOADED or PENDING_RELEASE
→ Authorized NIDO employee releases the license
→ Fulfillment becomes RELEASED
→ Client downloads the file
→ Download timestamp is recorded
→ Fulfillment becomes DOWNLOADED or COMPLETED

Do not build the detailed UI yet.

---

# 7. MINIMUM API SUPPORT

Inspect existing API patterns first.

Reuse existing Order and authentication patterns.

Add only the minimum backend endpoints required for the future Order Details UI.

Possible internal endpoints:

```text
GET /internal/orders/:orderId/digital-fulfillments
POST /internal/digital-fulfillments/:id/license
POST /internal/digital-fulfillments/:id/release
```

Possible client endpoint:

```text
GET /client/digital-fulfillments/:id/download
```

Use the project’s existing route naming conventions instead of blindly creating these exact routes.

Do not create duplicate APIs.

---

# 8. AUTHORIZATION

Reuse existing authentication and RBAC.

Internal actions such as:

* Upload license
* Replace license
* Enter or update password
* Release license
* View fulfillment details

must be restricted to authorized NIDO employees/admins.

Client actions must be restricted to:

* The client who owns the order
* The specific Digital Fulfillment linked to that order

Do not create a new authentication system.

---

# 9. DOWNLOAD SECURITY

The client must not be able to download the file before release.

Download rules:

1. Verify the user is authenticated.
2. Verify the user owns the related order.
3. Verify the Digital Fulfillment belongs to that order.
4. Verify status is RELEASED, DOWNLOADED, or COMPLETED as appropriate.
5. Reject access if status is PENDING, LICENSE_UPLOADED, PENDING_RELEASE, or CANCELLED.
6. Use a secure file response or signed URL according to the existing storage system.
7. Do not expose internal storage paths.
8. Record downloaded_at if not already recorded.
9. Record download activity if the existing audit system supports it.

Do not return the password to the client.

---

# 10. DIGITAL FULFILLMENT STATUS TRANSITIONS

Use controlled transitions.

Recommended transitions:

```text
PENDING
→ LICENSE_UPLOADED
→ PENDING_RELEASE
→ RELEASED
→ DOWNLOADED
→ COMPLETED
```

Cancellation may occur where appropriate:

```text
PENDING → CANCELLED
LICENSE_UPLOADED → CANCELLED
PENDING_RELEASE → CANCELLED
RELEASED → CANCELLED
```

Do not allow invalid transitions without authorization.

If the existing system has a status transition service, reuse it.

---

# 11. ORDER CREATION INTEGRATION

Integrate with the existing Order creation process.

When an order contains Digital Order Items:

* Create one Digital Fulfillment record per Digital Order Item.
* Set status to PENDING.
* Do not create a PO.
* Do not reserve physical inventory.
* Do not change the existing Client Order status.
* Do not split the order.

For mixed orders:

* Physical items continue through the existing PO and inventory flow.
* Digital items create Digital Fulfillment records.
* One Client Order remains.
