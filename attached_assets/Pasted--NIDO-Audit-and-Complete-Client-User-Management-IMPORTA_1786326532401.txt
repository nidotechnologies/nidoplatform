# NIDO – Audit and Complete Client User Management

## IMPORTANT INSTRUCTION

Do NOT rebuild, replace, or duplicate the existing NIDO authentication system, Client Portal, client management, database, user management, or protected-route system.

First perform a complete audit of the existing codebase and database.

Then identify what client-user-management functionality already exists.

Only implement the missing functionality.

Preserve all existing working functionality, UI, database records, authentication, routes, permissions, and client portal behavior.

Do not create duplicate tables, duplicate authentication flows, duplicate user-management pages, or duplicate roles if equivalent functionality already exists.

# 6. TWO ACCOUNT-CREATION METHODS

Support the following where compatible with the existing authentication architecture.

## Method A – Invitation

Recommended/default method.

Admin enters:

* Name
* Email
* Client
* Role
* Permissions

Admin clicks:

**Send Invitation**

User receives an invitation.

User opens invitation.

User creates their password.

Account becomes:

Invitation Pending

→ Invitation Accepted

→ Password Created

→ Active

Do not expose or store plaintext passwords.

Use the existing authentication provider's secure invitation/password setup mechanism.

---

# 7. METHOD B – ADMIN-CREATED CREDENTIALS

If supported by the existing authentication system, allow an NIDO Admin to create the user directly.

Admin can specify:

* Username/email
* Temporary password
* Client
* Role
* Permissions

The temporary password must never be stored as plaintext in the application database.

Prefer forcing:

**Change password on first login**

If the current authentication provider does not safely support admin-created passwords, do NOT implement a custom password system.

Instead use the existing authentication provider's invitation or password-reset mechanism.

---

# 8. USER STATUS

Support, where missing:

* Invited
* Active
* Inactive
* Suspended

Status changes must immediately affect authentication/authorization.

Example:

Inactive client user

→ Cannot access Client Portal.

Suspended client user

→ Cannot log in.

Do not merely hide the user in the UI; enforce the status at the authentication/authorization level.

# 10. CLIENT DATA ISOLATION

This is critical.

Every client user must be associated with exactly the appropriate client/tenant.

When a client user logs in:

User

→ Client ID

→ Client-specific data

The client user must only access:

* Their client's catalog
* Their client's pricing
* Their client's vendors where permitted
* Their client's cart
* Their client's orders
* Their client's invoices
* Their client's reports
* Their client's profile

A client user must NEVER be able to access another client's data by changing:

* URL parameters
* IDs
* API requests
* Query parameters
* Frontend state
* Browser storage

Enforce isolation on the backend/database level, not only in React.

# 18. IMPORTANT – NEW VENDOR WORKFLOW

Make sure client-user management works with the new procurement workflow.

The authenticated Client User must be able to:

1. Log into the Client Portal.
2. Open Shop.
3. View their client-specific catalog.
4. View eligible vendors.
5. See the recommended vendor.
6. Select a vendor.
7. Add the product to Cart.
8. Reserve stock against that selected vendor.
9. Checkout.
10. Place the order.
11. Automatically create Draft PO(s) for the selected vendor(s).

The Client User must not access another client's vendors or orders.

# 20. DATABASE SAFETY

Before modifying the database:

1. Identify existing schema.
2. Reuse existing tables where possible.
3. Do not create duplicate user tables.
4. Do not duplicate authentication records.
5. Do not duplicate client tables.
6. Preserve existing data.
7. Add migrations rather than destructive schema changes.
8. Preserve foreign keys.
9. Preserve tenant isolation.
10. Do not delete existing production records.

If a required field already exists under a different name, reuse it instead of creating another field.

# 22. TESTING REQUIREMENTS

After implementation, test all scenarios.

### Test 1

NIDO Admin creates a client user.

Expected:

User appears under the correct Client → Users & Access.

### Test 2

Admin sends invitation.

Expected:

Invitation status = Pending.

### Test 3

User accepts invitation.

Expected:

User creates password and account becomes Active.

### Test 4

User logs in.

Expected:

User enters the correct Client Portal.

### Test 5

User tries to access another client's order.

Expected:

Access denied.

### Test 6

Admin deactivates user.

Expected:

User cannot access the Client Portal.

### Test 7

Admin changes role.

Expected:

Permissions update correctly.

### Test 8

Admin resends invitation.

Expected:

Previous pending invitation is handled safely and a valid invitation is sent.

### Test 9

Client user purchases a product.

Expected:

Selected vendor is preserved through:

Shop → Cart → Order → Draft PO.

### Test 10

Multiple client users belong to the same client.

Expected:

They can access only the data permitted for that client and their assigned roles.
