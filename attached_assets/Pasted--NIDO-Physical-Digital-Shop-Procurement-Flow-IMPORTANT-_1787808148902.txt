# NIDO — Physical & Digital Shop Procurement Flow

## IMPORTANT IMPLEMENTATION RULE

Do NOT rebuild, redesign, or replace existing NIDO modules.

The current NIDO procurement flow is already implemented and working. Extend the existing implementation with the minimum possible code/database/UI changes.

**Priority:**

1. Reuse existing components, APIs, database models, services, and UI.
2. Do not duplicate Product, Vendor, Client Catalogue, Cart, Checkout, Order, or PO systems.
3. Do not create a separate Digital Shop application/module.
4. Do not change the existing Physical Product procurement workflow except where required to support Digital Products.
5. Do not build the detailed Digital Order Details page UI yet. Only create the backend/data structure and basic status needed for it. The detailed Order Details UI will be implemented later.
6. Before changing anything, inspect the existing codebase and identify the existing models, APIs, pages, components, and services that already handle this flow.
7. Make small incremental changes only.
8. Do not generate unnecessary files, mock data, duplicate components, or new frameworks.
9. Preserve all existing functionality.

---

# EXISTING NIDO PROCUREMENT FLOW

The existing system works as follows:

Master Catalogue
→ Publish Product
→ Assign Product to Vendor
→ Enter Vendor Price, MOQ, Lead Time, Stock
→ Add Product to Client Catalogue
→ Configure Client Roles, Preference and Client Pricing
→ Product Appears in Shop
→ Client Selects Vendor
→ Product Added to Cart with Vendor Snapshot
→ Checkout
→ Delivery Details
→ Payment Details
→ Review Order
→ Place Order
→ Client Order Created
→ Vendor Stock Reserved
→ One Draft PO Automatically Created per Selected Vendor
→ Admin Reviews Draft PO
→ Confirm / Reject PO
→ Confirmed PO processed in Vendor Orders
→ Processing → Shipped → Delivered

This existing Physical Product flow must continue working exactly as it does today.

## 1. Physical Shop

## 2. Digital Shop

Use the existing Shop page and existing Shop infrastructure.

* Client Catalogue

* Cart

→ Digital Shop
→ View Digital Product

→ Checkout

* No customer vendor selection
* No vendor selection modal

* No automatic PO generation
* No physical delivery requirement

# DIGITAL VENDOR/SUPPLIER RULE

Do NOT remove the vendor relationship from Digital Products.

Digital products may still have an internal vendor/supplier.

The difference is:

### Physical

Customer selects the vendor.

### Digital

NIDO internally uses the configured digital supplier/vendor.

The customer must never be required to select the vendor.

If the existing vendor-product relationship already exists, reuse it.

Add the minimum required field to identify the preferred/default supplier only if the existing system does not already have an equivalent mechanism.

For example:

* preferred vendor
* default vendor
* primary vendor

Use an existing equivalent field if one already exists.

Do not create duplicate supplier structures.

# PO GENERATION RULE — VERY IMPORTANT

Modify the existing automatic PO generation logic minimally.

Current behavior:

One Draft PO per selected vendor.

New rule:

## Only Physical Order Items can generate POs.

Pseudo logic:

IF Order Item Product Type = Physical
AND PO Required = true
→ include item in PO grouping.

IF Order Item Product Type = Digital
OR PO Required = false
→ do NOT generate PO.

Then group eligible Physical Order Items by vendor exactly as the current system does.

Example:

Order contains:

Laptop → Physical → Vendor A
Monitor → Physical → Vendor A
Microsoft License → Digital → Vendor C

Result:

PO-001
Vendor A

* Laptop
* Monitor

No PO for Microsoft License.

The Digital item goes to Digital Fulfillment.

Do not create a fake PO for Digital Products.

# DIGITAL LICENSE WORKFLOW

Prepare the backend for this future workflow:

Order Created
→ Digital Fulfillment = PENDING
→ NIDO employee uploads password-protected license file
→ NIDO employee manually enters the file password
→ File stored securely
→ Password stored securely/encrypted
→ NIDO employee releases license
→ Client can download
→ Client downloads file
→ Client uses manually provided password to open the protected file
→ Digital Fulfillment completed

Do not implement the detailed employee/client Order Details UI yet.

Only implement the underlying status/data structure and API support necessary for the later UI.

# SECURITY REQUIREMENTS

For the digital license file:

1. Do not expose the file before release.
2. Do not expose the internal password to the client through the API.
3. Do not store the password as plain text.
4. Only authorized NIDO users should be able to upload/release the file.
5. Client access must verify that the file belongs to that client's order.
6. Download must only be available after RELEASED status.
7. Record download activity if the existing audit system supports it.
8. Reuse existing authentication and authorization/RBAC.
9. Do not create a new authentication system.
